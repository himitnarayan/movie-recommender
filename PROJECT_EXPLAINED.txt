INTRODUCTION — WHAT IS THIS PROJECT AND WHY DID I BUILD IT?
================================================================================

A recommender system is one of the most valuable and practical applications of
Machine Learning. Every major tech company uses them:
  - Netflix recommends movies
  - Spotify recommends songs
  - Amazon recommends products
  - YouTube recommends videos

Most tutorials teach you to build a "basic" recommender using TF-IDF cosine
similarity on a small 5,000-movie dataset that only runs on your laptop. That
is completely useless in a real job because:

  1. It cannot scale beyond a few thousand items
  2. It only does keyword matching, not semantic understanding
  3. It cannot be deployed to the cloud without crashing from RAM usage
  4. It has no explainability (users don't know WHY something was recommended)
  5. It has no way to measure if it's actually better than a simpler model

This project solves ALL five of those problems. It is built exactly the way
a team of professional ML Engineers at a real company would build it.


================================================================================
STEP 1 — STARTING SIMPLE (TF-IDF LOCAL MODEL)
================================================================================

WHY: Every good engineering project starts simple and evolves. We began with
the most basic approach so we could understand the problem before improving it.

WHAT WE DID:
  - Loaded a small TMDB movie dataset (~5,000 movies) from Kaggle using Pandas
  - Combined each movie's title, genres, and overview into one "soup" string
    Example: "The Dark Knight Action Crime A vigilante fights the Joker..."
  - Applied TF-IDF (Term Frequency — Inverse Document Frequency) vectorization
    TF-IDF converts text into numbers based on how often words appear
  - Used cosine similarity to find movies with the closest matching vectors
  - Stored the resulting FAISS index and TF-IDF matrix as local .pkl/.bin files
  - Built a Django web app with a search bar to query the local model

THE PROBLEM WE DISCOVERED:
  - TF-IDF only matches exact keywords. If a user types "space adventure",
    it would NOT find "Guardians of the Galaxy" because those exact words don't
    appear in its overview. It has no understanding of meaning.
  - The FAISS index and TF-IDF matrix consumed 1.5GB of RAM
  - Render's free hosting tier only gives 512MB of RAM
  - The app immediately crashed when deployed to the cloud
  - Conclusion: We needed a fundamentally better architecture


================================================================================
STEP 2 — MOVING TO CLOUD VECTOR DATABASE (PINECONE)
================================================================================

WHY: The RAM problem is not solved by writing better code — it's solved by
changing the architecture. Instead of storing the ML model ON the web server,
we store it in a DEDICATED cloud database designed specifically for this job.

This is the same architectural decision Netflix, Spotify, and LinkedIn made.
They don't load 100 million song embeddings into their web servers. They store
them in dedicated vector databases (like Pinecone, Weaviate, or Qdrant) and
query them via API.

WHAT WE DID:
  - Created a free Pinecone Serverless account (AWS us-east-1 region)
  - Created an index with 384 dimensions and "dotproduct" metric
    WHY dotproduct? Because it's required for hybrid (sparse + dense) search
  - Wrote a Google Colab training script to generate and upload all vectors
  - The Django server now only makes API calls — it stores NOTHING in RAM
  - Result: Django server RAM usage dropped from 1.5GB to under 100MB

KEY INSIGHT:
  Pinecone charges you for storage, not for your web server's RAM. This means
  you can query 1 billion vectors from a 512MB web server — the database does
  all the heavy lifting in the cloud.


================================================================================
STEP 3 — UPGRADING FROM TF-IDF TO HYBRID SEARCH
================================================================================

WHY: TF-IDF is keyword matching. Neural embeddings understand MEANING.
We wanted both — the precision of keywords AND the intelligence of semantics.

PART A — DENSE VECTORS (SEMANTIC SEARCH)
  A "dense vector" is a list of 384 numbers that represents the MEANING of a
  piece of text, not just its keywords.

  Example:
    "a film about a masked hero fighting crime in a dark city"
    → [0.23, -0.45, 0.89, 0.12, ...] (384 numbers)

    "The Dark Knight" overview:
    → [0.21, -0.43, 0.91, 0.10, ...] (384 numbers — very similar!)

  These vectors were generated using HuggingFace's "all-MiniLM-L6-v2" model,
  which is a small, fast, 384-dimensional Sentence Transformer trained on
  hundreds of millions of sentence pairs. It is the industry-standard choice
  for semantic similarity on a budget.

PART B — SPARSE VECTORS (KEYWORD SEARCH)
  Even with semantic search, exact keyword matching still matters. If a user
  types the exact title "The Matrix Reloaded", we want that movie to rank #1,
  not just movies that are "vibes-similar" to The Matrix.

  We used BM25Encoder from the "pinecone-text" library.
  BM25 (Best Match 25) is the gold standard for keyword search — it's the
  same algorithm that powers Elasticsearch and Google's early search engine.
  It is better than TF-IDF because it handles:
    - Term saturation (mentioning "action" 50 times shouldn't overweight it)
    - Document length normalization (longer movies won't unfairly dominate)

PART C — HYBRID FUSION
  Pinecone's query endpoint accepts BOTH a dense vector and a sparse vector
  simultaneously. It combines them using an "alpha" parameter:
    - alpha = 1.0 → pure semantic search
    - alpha = 0.0 → pure keyword search
    - alpha = 0.5 → equal mix of both (what we use)

  This single API call does what used to require two separate systems.

THE EMBEDDING MISMATCH PROBLEM (AND HOW WE SOLVED IT):
  When we changed the query-time embedding model, we discovered a critical rule:
  THE MODEL USED AT TRAINING TIME MUST EXACTLY MATCH THE MODEL USED AT QUERY TIME.

  If you index movies using Model A and then search using Model B, even if both
  produce 384-dimensional vectors, they live in completely different mathematical
  spaces. The similarity scores will be meaningless — like using a French map
  to navigate a Spanish city just because both maps are the same size.

  Solution: We standardized on "all-MiniLM-L6-v2" for BOTH training (Colab)
  and inference (Django), ensuring both sides speak the same mathematical language.


================================================================================
STEP 4 — GOOGLE COLAB GPU TRAINING PIPELINE
================================================================================

WHY: Generating 17,000+ embeddings is computationally expensive. A CPU would
take hours. A GPU takes minutes. Google Colab gives us a free T4 GPU.

More importantly, this decouples "training" from "serving" — exactly how
real ML teams operate. The Data Scientists handle training. The Engineers
handle serving. They don't happen on the same machine.

WHAT WE DID:
  - Wrote a standalone Python script (colab_training_script.py)
  - It downloads the Kaggle TMDB 930k dataset (243MB compressed)
  - Cleans the data: drops null titles/overviews, coerces corrupt IDs to NaN
    and drops them, handles malformed CSV rows that crash standard parsers
  - Combines title + genres + overview into a "soup" for each movie
  - Generates dense embeddings in batches of 96 using the HuggingFace model
  - Generates sparse BM25 vectors for each movie
  - Uploads everything to Pinecone in batches (avoids API timeouts)
  - Saves the fitted BM25 model as "bm25_params.json"

DATA CLEANING CHALLENGES FACED:
  The TMDB Kaggle dataset is a notoriously messy real-world CSV. We encountered:
  - "EOF inside string" errors: unclosed quotes in movie overviews
    Fix: Used Pandas Python engine with on_bad_lines='skip'
  - Column misalignment: commas in titles shifted all column data right
    Fix: Coerced the ID column to numeric; any bad row becomes NaN and is dropped
  - Non-ASCII characters in IDs: symbols like "²" in movie IDs
    Fix: Converted all IDs to integer then to string before Pinecone upload
  - Null poster_path values: Pinecone rejects null metadata values
    Fix: Replaced all NaN poster paths with empty string ""
  - Empty sparse vectors: movies with no text produce empty BM25 vectors
    Fix: Only include sparse_values in the upsert record if indices are non-empty

  These are the exact same data quality problems you encounter in production
  data engineering work at real companies. Solving them is a key skill.

STEP 5 — EXPLAINABLE AI (GOOGLE GEMINI INTEGRATION)
================================================================================

WHY: Recommender systems are "black boxes." The user sees 10 movie posters
but has no idea WHY the system chose them. This damages trust.

Explainability (XAI) is increasingly mandatory in enterprise AI:
  - EU's AI Act requires explanations for automated decisions
  - Financial AI must explain loan recommendation decisions
  - Healthcare AI must explain treatment recommendations

We solved this by integrating Google Gemini 2.5 Flash.

WHAT WE DID:
  After retrieving the top recommendation from Pinecone, we send:
  1. The user's original query
  2. The recommended movie's title
  3. The first 300 characters of the movie's overview

  We then ask Gemini: "In one short sentence, explain why someone who likes
  [query] would also like [movie]."

  Gemini returns something like:
  "You'll love this because it shares the same gritty detective atmosphere
   and morally complex protagonist as your search."

  This turns a cold similarity score into a warm, human explanation.

WHY GEMINI FLASH SPECIFICALLY:
  - Extremely fast inference (< 1 second response time)
  - Free tier is generous (60 requests/minute)
  - Better than local open-source LLMs which would consume 4GB+ of RAM


================================================================================
STEP 6 — CONTAINERIZATION WITH DOCKER
================================================================================

WHY: "It works on my machine" is not acceptable in professional engineering.
Docker ensures the application runs identically on every machine and every
cloud provider, with no dependency conflicts or environment differences.

WHAT WE DID:
  - Wrote a Dockerfile that starts from the official Python 3.10 slim image
  - Installs all requirements from requirements.txt
  - Runs the app using Gunicorn (production-grade WSGI server)
  - Wrote a docker-compose.yml for easy local development with one command:
    "docker-compose up --build"

WHY GUNICORN INSTEAD OF DJANGO'S BUILT-IN SERVER:
  Django's development server (manage.py runserver) is single-threaded and
  not designed to handle concurrent requests. Gunicorn spawns multiple worker
  processes that can handle multiple users simultaneously. This is mandatory
  for production deployments.

STEP 7 — A/B TESTING FRAMEWORK
================================================================================

WHY: "My new algorithm is better" is an opinion. A P-Value is a fact.
In data science, you must prove improvements with statistical evidence.
This is how companies like Amazon and Google make product decisions.

WHAT WE DID:
  Built ab_test_simulator.py which:
  1. Creates a ground-truth "genre cluster" system (comedy movies cluster
     together, action movies cluster together, etc.)
  2. Simulates 1,000 virtual users — 500 in Group A (TF-IDF), 500 in Group B (Hybrid)
  3. Each user queries a random movie. We check if the top 5 recommendations
     belong to the same genre cluster (a "relevant" click)
  4. Calculates Click-Through Rate (CTR) for each group
  5. Runs scipy.stats.ttest_ind() — a Two-Sample T-Test
  6. Outputs a P-Value

  P-Value interpretation:
  - P < 0.05 → The improvement is statistically significant (not random luck)
  - P > 0.05 → Cannot declare a winner yet (need more data or a bigger effect)

RESULT:
  The A/B test showed the Hybrid model outperformed pure TF-IDF on semantic
  queries, but the difference was small enough that more data would be needed
  to declare statistical significance in a real production scenario.


================================================================================
STEP 8 — CLOUD DEPLOYMENT ON RENDER
================================================================================

WHY: A project that only runs locally is a homework assignment.
A project that runs on the internet, 24/7, for real users is a portfolio piece.

WHAT WE DID:
  - Connected GitHub repository to Render
  - Created a build.sh script that Render runs on every push to main:
      pip install -r requirements.txt
      python manage.py collectstatic --noinput
  - Set Start Command: gunicorn moviesite.wsgi:application --bind 0.0.0.0:$PORT
  - Added 3 environment variables on Render's dashboard:
      PINECONE_API_KEY → connects to our cloud vector database
      GOOGLE_API_KEY   → connects to Gemini for XAI explanations
      HF_TOKEN         → authenticates with HuggingFace for embedding generation

CHALLENGES FACED DURING DEPLOYMENT:
  1. Out of Memory (OOM) crash:
     Cause: sentence-transformers + PyTorch uses 400MB just to import
     Fix: Removed those libraries entirely. Used HuggingFace's Inference API
          instead — the model runs on HuggingFace's servers, not ours

  2. Port binding failure:
     Cause: Gunicorn was binding to a fixed port, but Render assigns a
            dynamic port via the $PORT environment variable
     Fix: Changed start command to use --bind 0.0.0.0:$PORT

  3. Old code still running after push:
     Cause: Code was on the ds-improvements branch, not main
     Render only deploys from the main branch
     Fix: Merged ds-improvements into main via git merge

  4. Build script trying to run build_model.py:
     Cause: Old build.sh was downloading Kaggle data and training models
            during deployment — which doesn't make sense in the cloud era
     Fix: Simplified build.sh to only install packages and collect static files
          The heavy training now happens separately in Google Colab

FINAL ARCHITECTURE SUMMARY — WHY EACH DECISION WAS MADE
================================================================================

DECISION                        | REASON
--------------------------------|----------------------------------------------
Pinecone instead of local FAISS | Local FAISS requires ~1.5GB RAM — crashes
                                | Render free tier (512MB). Pinecone stores
                                | vectors in the cloud, server uses <100MB.
--------------------------------|----------------------------------------------
HuggingFace Inference API       | sentence-transformers + PyTorch = 400MB RAM
instead of local model          | just for imports. HF API runs the model on
                                | their servers. Our server stays lean.
--------------------------------|----------------------------------------------
Google Colab for training       | Training 17k embeddings takes minutes on
instead of local machine        | a T4 GPU, hours on a CPU. Colab is free.
                                | Also cleanly separates training from serving.
--------------------------------|----------------------------------------------
Hybrid Search (BM25 + Dense)    | Dense alone fails on exact title matches.
instead of just semantic search | BM25 alone fails on semantic queries.
                                | Together they cover all query types.
--------------------------------|----------------------------------------------
Gemini for explanations         | Turns a black-box score into a human-readable
instead of no explanations      | justification. Builds user trust and
                                | demonstrates XAI skills to employers.
--------------------------------|----------------------------------------------
Docker for packaging            | Eliminates "works on my machine" problems.
instead of bare Python          | Same image runs on any cloud provider.
--------------------------------|----------------------------------------------
Django instead of Flask         | Django includes ORM, admin panel, auth,
                                | and static file serving out of the box.
                                | Better for a production-grade project.
--------------------------------|----------------------------------------------
Render for hosting              | GitHub integration for auto-deploy.
instead of local ngrok          | Permanent URL. Free tier sufficient since
                                | we offloaded the heavy ML to Pinecone.
